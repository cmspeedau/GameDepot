# Client API reference

The HTTP contract between the desktop client and the server. It is defined here and
nowhere else. Field names, status codes and error shapes are fixed once a client ships.

Everything here describes the target server. None of it is implemented yet.

## Conventions

- Base URL: the origin the user configured in the client, e.g. `https://games.example`.
- All paths below are relative to that origin.
- JSON in, JSON out, unless noted. Requests send `Content-Type: application/json`.
- Timestamps are ISO 8601 with milliseconds and a `Z` suffix.
- Ids are UUIDv7 strings generated by the server.
- Authentication is per request. There is no session cookie on the client API.

### Error shape

```json
{
  "error": {
    "code": "not_found",
    "message": "Game not found",
    "fields": { "name": "required" }
  }
}
```

`fields` is present only for validation errors. Status codes: 400 malformed, 401
unauthenticated, 403 forbidden, 404 missing, 409 conflict, 422 validation, 429 rate
limited, 500 internal. A client must treat any 4xx as a non-retryable failure and any
5xx as retryable with backoff.

### Profile and device

A client token is bound to one user and one device. There is no profile selector in v1;
playtime and collections belong to the user. A device can be revoked from the dashboard.

## Pairing

### 1. Initiate

```http
POST /api/v1/pairing/initiate
Content-Type: application/json

{ "name": "Living room deck", "platform": "linux" }
```

`platform` is `linux`, `windows` or `macos`. Unknown values are 422.

Response:

```json
{ "code": "ABCD1234", "expiresAt": "2026-11-15T12:10:00.000Z" }
```

The code is eight characters in Crockford base32, uppercase, valid for ten minutes. Rate
limited per IP.

### 2. Approve

In the dashboard, the user enters the code and confirms. The code is bound to the
signed-in user. Until approval, claiming returns `409`.

### 3. Claim

```http
POST /api/v1/pairing/claim
Content-Type: application/json

{ "code": "ABCD1234" }
```

Response, once:

```json
{ "clientId": "<uuid>", "token": "<base64url, 32 bytes>" }
```

The token is shown once. The server stores a SHA-256 hash. A second claim of the same
code returns 410. An unapproved code returns 409. An expired code returns 410.

### Authenticated requests

```text
Authorization: Bearer <token>
```

A missing header is 401. An unknown or revoked token is 401. A valid token without the
required scope is 403.

## Server version

### `GET /api/v1/version`

Unauthenticated. Reports the server build for upgrade and compatibility checks:

```json
{ "version": "0.1.0" }
```

Clients compare against the version they were built for and the release notes shipped
with the server. A client that needs a newer schema refuses to sync and shows the
required version rather than failing on an individual request.

## Library

### `GET /api/v1/library`

Games the user can access, with the installed version id if present:

```json
[
  {
    "id": "<uuid>",
    "name": "Game",
    "summary": "...",
    "coverUrl": "/api/v1/objects/<id>",
    "installedVersionId": "<uuid>" | null
  }
]
```

### `GET /api/v1/games/{id}`

Full game record.

### `GET /api/v1/games/{id}/versions`

```json
[
  {
    "id": "<uuid>",
    "name": "1.2.0",
    "platform": "windows",
    "totalSize": 123456,
    "releasedAt": "2026-11-15T12:00:00.000Z"
  }
]
```

### `GET /api/v1/games/{id}/recipe`

The runner recipe for a game, when the operator has recorded one: how this title is
expected to start, which compatibility runner it wants, and how well it is known to work.
Add `?versionId=<id>` for a release-specific recipe; without it the game-level recipe
applies. `404` with `{"code":"not_found"}` when none exists, which is the normal case and
not an error - a game with no recipe is launched by the client's own defaults.

```json
{
  "id": "<uuid>",
  "gameId": "<uuid>",
  "versionId": "",
  "profile": {
    "launch": {
      "mode": "store_client",
      "store": "uplay",
      "handler": "uplay://launch/{app}/0",
      "requires": ["client_installed", "client_signed_in"]
    },
    "runner": { "kind": "umu", "build": "GE-Proton9-27" },
    "env": {}
  },
  "source": "curated",
  "compatibility": "untested",
  "createdAt": "2026-11-18T09:30:00Z",
  "updatedAt": "2026-11-18T09:30:00Z"
}
```

`launch.mode` is `direct` (the file tree starts on its own, natively or through umu) or
`store_client` (the provider's own client must start it, so entitlement stays the
provider's answer - see ADR-0012). `source` is `curated` or `observed`. `compatibility` is
`untested`, `works`, `works_with_tweaks` or `broken`, and is only ever set from a real
attempt on a real prefix.

Two limits to know, both current rather than intended. `profile` is stored as an opaque
document: the shape above is the agreed one (ADR-0012) but the server does not validate
keys, and an unreadable profile is served as `null` rather than failing the request. And
there is no write path yet - recipes are created by direct SQL today, and the desktop does
not yet call this endpoint. The admin form and the client consumption are tracked in the
roadmap.

### `GET /api/v1/releases/{versionId}`

```json
{
  "digest": "<hex>",
  "totalSize": 123456,
  "manifestUrl": "/api/v1/depot/manifests/<digest>",
  "launches": [
    { "id": "<uuid>", "name": "Play", "platform": "linux",
      "executable": "bin/game", "arguments": ["--launch"], "workingDir": "" }
  ]
}
```

The manifest URL is a convenience; the client may build it from the digest. `launches`
are the executable options for the version: `executable` is relative to the install
root and must stay inside it; `arguments` are passed as an array (never through a
shell). See `GET /api/v1/games/{id}/versions` for the version list that precedes this.

## Depot

### `GET /api/v1/depot/manifests/{digest}`

Returns the manifest JSON from section 9 of `ARCHITECTURE.md`. Authenticated and
authorized for the game that owns the release. 404 when missing.

### `GET /api/v1/depot/objects/{sha256}`

Returns ciphertext bytes. No range support in v1. 404 when the object is not in any
release the caller can access.

### `GET /api/v1/depot/healthcheck`

200 with an empty body when the depot root is readable.

## Playtime

### `GET /api/v1/playtime`

All playtime rows for the user:

```json
[{ "gameId": "<uuid>", "seconds": 3600, "lastPlayedAt": "..." }]
```

### `POST /api/v1/playtime`

```json
{ "gameId": "<uuid>", "seconds": 600 }
```

Adds the delta to the existing row. `seconds` must be between 1 and 31,536,000. An
unknown game is 404. Returns the updated row.

## Collections

### `POST /api/v1/collections`

```json

```

### `DELETE /api/v1/collections/{id}`

Removes the collection and its entries.

## Cloud saves

Versioned save archives per (user, game, slot). The archive is an opaque blob (the
desktop packs matched save files into a `tar.zstd`); the server stores it content-
addressed and tracks versions with optimistic concurrency. Requires the `saves:read` or
`saves:write` scope on the client token.

The server does not open the archive. Integrity of the bytes is the archive SHA-256;
the logical `contentHash` (a hash of the client's file set: key, size, per-file hash,
mode) is supplied by the client and used only for sync decisions and dedup. This mirrors
Ludusavi's client-side content identity.

### `GET /api/v1/saves`

Slots for the caller, optionally `?game=<id>`:

```json
[{ "id": "...", "gameId": "...", "slotIndex": 0, "label": "manual",
   "headVersionId": "...", "createdAt": "...", "updatedAt": "..." }]
```

### `GET /api/v1/saves/manifests/{gameId}`

The save-location roots the server holds for the game (the user-defined manifest).
`platform` is `windows|linux|macos|*`, `kind` is `file|registry`.

```json
{ "gameId": "...", "paths": [
  { "id": "...", "platform": "linux", "kind": "file",
    "template": "{user}/.local/share/{p}/**", "recursive": true } ] }
```

The desktop expands a template into a local directory before collecting files:

| Placeholder | Expands to |
| --- | --- |
| `{user}`, `{home}` | the user's home directory |
| `{p}`, `{name}` | the game's name from the library list |
| `{appdata}` | the platform config/data directory |

On Linux this is `XDG_CONFIG_HOME`, on Windows `%APPDATA%`, on macOS
`~/Library/Application Support`.

A `/**` or `/*` suffix is stripped; `recursive` already says whether to walk
subdirectories. Only `kind: file` roots whose platform matches the caller's (or
`*`) are used; registry roots and other platforms are skipped. Any other
placeholder (for example `{steamid}`, which needs a provider the desktop lacks)
fails the save loudly rather than creating a directory named `{steamid}`.

The desktop keeps a per-(game, slot) sync cursor of the last base sequence and
content hash it agreed with the server. On sync it compares local-changed with
server-changed and picks one of four outcomes: push (local ahead), pull (server
ahead), noop (equal) or conflict (both moved). A conflict never auto-resolves;
the user picks "use server" (download the head over the local files) or "keep
mine" (push the local set over the head, keeping the previous head in history).

### `POST /api/v1/saves/slot/{gameId}/{slot}/push`

Streams the archive as the request body. Headers:

- `X-Content-Hash` (required): the client's logical hash for this save set.
- `X-Base-Seq` (optional, default 0): the version sequence the client built on.
- `X-File-Count` (optional).

Response is the created version. Outcomes:

- `200` with the version: a new head was created.
- `200` with `{"noop":true,"headVersionId":...}`: the content already equals the head.
- `409` with `{"error":{"code":"conflict"},"headSeq":n,"headVersionId":...}`: the head
  moved past the base and content differs; pull or rebase before pushing.

### `GET /api/v1/saves/slot/{gameId}/{slot}/download[?seq=n]`

The head archive (or a specific version). Serves the stored blob bytes with an `ETag`
of its content hash. `404` when the slot or version does not exist.

### `GET /api/v1/saves/slot/{gameId}/{slot}/versions`

All versions of the slot, newest sequence first:

```json
[{ "id": "...", "seq": 2, "kind": "save", "contentHash": "h2",
   "archiveSha256": "...", "size": 12, "fileCount": 0, "pinned": false, "createdAt": "..." }]
```

`kind` is `save` (a client push) or `restore` (an older version made current).

### `POST /api/v1/saves/slot/{gameId}/{slot}/versions/{versionId}/restore`

Adds a new `restore` version that reuses the target's archive and makes it the head.
`409` if the head moved concurrently.

### `POST /api/v1/saves/slot/{gameId}/{slot}/versions/{versionId}/pin`

Pins or unpins (default pinned; `?pinned=false` to unpin). Pinned versions are never
pruned and cannot be deleted.

### `DELETE /api/v1/saves/slot/{gameId}/{slot}/versions/{versionId}`

Deletes an unpinned, non-head version. Returns `409` when the version is the head or is
pinned.

Retention: each slot keeps the head plus the most recent `10` unpinned versions; older
ones are pruned on push. Stored archive blobs are content-addressed and shared, so the
server does not delete blob files on prune (dedup keeps storage bounded).

## Objects

### `GET /api/v1/objects/{id}`

Small object (cover, icon, avatar). Streams from disk with the correct content type and
an `ETag`. `If-None-Match` returns 304. Access is checked against the row referencing
the object.

## Tasks

Phase 4 and later. Reserved namespace:

```text
GET /api/v1/tasks/{id}
```

Returns `{ "id", "kind", "state", "progress", "log": [] }`. The dashboard reaches the
same data through HTMX fragments.

## WebSockets

None in v1. Pairing is polled. Tasks are polled by the dashboard. The desktop does not
need a socket.

## Compatibility

There is none. This is a new product. The server does not accept tokens, cookies or
manifests from any other implementation, and clients from other implementations cannot
pair with it.
